# 1.5 动态缓存块管理 🧱

> **目标**：在 paged KV-Cache 之上构建一个**动态、可回收、可压缩**的块生命周期系统，支持运行期间增删块、KV 压缩裁剪、抢占恢复以及前缀缓存共享。

---

## 🧬 1.5.1 块的生命周期

```
                ┌───────────────┐
   分配 ───────▶│   USED, ref≥1 │──── append ─────▶ 仍 USED
                └──────┬────────┘
                       │ deallocate / truncate
                       ▼
                ┌───────────────┐
                │   FREE, ref=0 │
                └───────────────┘
```

每个块的状态由 `Block`（`KvChat/engine/block_manager.py`）持有：

```python
class Block:
    def __init__(self, block_id):
        self.block_id  = block_id
        self.ref_count = 0          # 共享计数
        self.hash      = -1         # 块内容指纹（满块时计算）
        self.token_ids = []         # 满块时缓存的 token 列表
```

`hash == -1` 代表"块尚未填满或内容已被改写"，**不参与前缀缓存匹配**。

---

## 🧰 1.5.2 BlockManager 的双视图

```python
self.blocks: list[Block]                     # 静态：全部物理块
self.free_block_ids: deque[int]              # 动态：空闲池
self.used_block_ids: set[int]                # 动态：占用池
self.hash_to_block_id: dict[int, int]        # 内容寻址：前缀缓存索引
```

| 视图 | 用途 | 复杂度 |
| --- | --- | --- |
| `free_block_ids` | 弹出空闲块（`deque[0]`） | O(1) 头部读 |
| `used_block_ids` | 集合判定是否已分配 | O(1) |
| `hash_to_block_id` | 哈希到块 id 的反向索引 | O(1) 平均 |

---

## ➕ 1.5.3 动态分配：`allocate(seq)`

Prefill 准入时一次性为序列预分配 `seq.num_blocks` 个块：

```python
for i in range(seq.num_blocks):
    token_ids = seq.block(i)
    h = compute_hash(token_ids, h) if len(token_ids)==block_size else -1
    block_id = self.hash_to_block_id.get(h, -1)

    if block_id != -1 and block.hash == h and block.token_ids == token_ids:
        # ✅ 前缀缓存命中：共享 + ref_count++
        seq.num_cached_tokens += block_size
        block.ref_count += 1
    else:
        # ❌ Cache miss：占用一个空闲块
        block_id = self.free_block_ids[0]
        block = self._allocate_block(block_id)

    if h != -1:
        block.update(h, token_ids)
        self.hash_to_block_id[h] = block_id
    seq.block_table.append(block_id)
```

📌 关键设计：

- 🔐 **三重校验**：`hash + token_ids + ref_count`，避免 xxhash 冲突造成"内容错位"。
- 📊 **冲突统计**：`collision_stats` 计数 `total_hashes` / `collisions`，便于运维诊断。
- 🪶 **零拷贝共享**：多个 Sequence 的 `block_table` 中可以指向同一物理块（典型如多轮对话的 system prompt）。

## ➕ 1.5.4 动态追加：`may_append(seq)`

Decode 阶段每生成 1 个 token 都可能涉及尾块状态变化：

```python
if len(seq) % block_size == 1:
    # 上一步刚好填满 → 现在需要一个新块
    block_id = self.free_block_ids[0]
    self._allocate_block(block_id)
    block_table.append(block_id)

elif len(seq) % block_size == 0:
    # 当前 token 把最后一块写满 → 计算哈希并入 dict
    token_ids = seq.block(seq.num_blocks - 1)
    prefix    = self.blocks[block_table[-2]].hash if len(block_table) > 1 else -1
    h         = self.compute_hash(token_ids, prefix)
    last_block.update(h, token_ids)
    self.hash_to_block_id[h] = last_block.block_id

else:
    # 中间状态：不计算 hash，hash 仍为 -1
    assert last_block.hash == -1
```

> 🧠 仅在**写满**时计算并登记哈希，因为只有满块才能作为稳定的"前缀缓存单位"。

`can_append(seq)` 是它的轻量预检：

```python
def can_append(self, seq):
    return len(self.free_block_ids) >= (len(seq) % self.block_size == 1)
```

只在"恰好填满+1"那一步要求至少 1 个空闲块。

## ➖ 1.5.5 动态释放：`deallocate(seq)`

```python
for block_id in reversed(seq.block_table):
    block = self.blocks[block_id]
    block.ref_count -= 1
    if block.ref_count == 0:
        self._deallocate_block(block_id)   # 回到 free_block_ids
seq.num_cached_tokens = 0
seq.block_table.clear()
```

**逆序遍历**保证：当多个序列共享前缀块时，先归还尾部独占块，更利于 free 池的局部性。

`_deallocate_block` 仅做归池处理，**不清除 `Block.hash` / `token_ids`**——这是**前缀缓存的"软回收"**：等到该块被下一个序列重新 reset 时才彻底失效。

## ✂️ 1.5.6 KV 压缩驱动的动态裁剪：`truncate_blocks`

KV 压缩 (`MyCompressCompact`) 完成 `S → R` 的紧凑后，通过 `compression_events` 通知调度器：

```python
def truncate_blocks(self, seq, keep_blocks):
    if keep_blocks >= len(seq.block_table):
        return
    tail = seq.block_table[keep_blocks:]
    for block_id in reversed(tail):
        block = self.blocks[block_id]
        block.ref_count -= 1
        if block.ref_count == 0:
            self._deallocate_block(block_id)

    seq.block_table = seq.block_table[:keep_blocks]
    seq.num_cached_tokens = min(seq.num_cached_tokens, keep_blocks * self.block_size)

    if seq.block_table:
        last_block = self.blocks[seq.block_table[-1]]
        if last_block.hash != -1:
            last_block.hash = -1   # 🚫 让其退出前缀缓存
```

为什么要清 last_block.hash？因为 `MyCompressCompact` 把"压缩后的前 R 个槽"重写到该块，原始内容已不存在，**保留旧 hash 会污染前缀缓存**。

## 🌀 1.5.7 抢占恢复链路

`Scheduler.preempt(seq)` 在 Decode 显存不够时被触发：

```python
seq.status = SequenceStatus.WAITING
seq.num_tokens = len(seq.token_ids)
seq.last_token = seq.token_ids[-1]
self.block_manager.deallocate(seq)               # 🧹 释放所有块
heapq.heappush(self.waiting_heap, (len(seq), seq.seq_id, seq))
```

恢复时：

1. `Scheduler.schedule()` 从 heap 弹出该序列，再走 `block_manager.allocate(seq)`。
2. 由于前缀缓存机制，**之前满块的内容大概率还在 `hash_to_block_id` 里**，能命中、不需重算 prefill。
3. `num_cached_tokens` 恢复到块对齐位置，`prepare_prefill` 自动只对未缓存部分重新计算。

> 🪄 这是 KvChat 用最低成本实现"软抢占 + 部分续算"的关键。

## 📈 1.5.8 池化与监控

| 指标 | 出处 | 说明 |
| --- | --- | --- |
| `len(free_block_ids)` | `BlockManager` | 实时空闲块数 |
| `collision_stats.collisions` | `BlockManager` | 哈希冲突总数（warning 级日志） |
| `compression_events` 数量 | `Scheduler.postprocess` | 当前 step 内压缩动作数 |
| `peak_memory_reserved_gb` | `LLMEngine.session_stats` | torch 已保留显存峰值 |

通过 `LLM.print_session_stats()` 可一键打印吞吐、显存、批次效率，便于分析"块管理是否成为瓶颈"。

## 🧠 1.5.9 设计权衡

| 权衡点 | 选择 | 理由 |
| --- | --- | --- |
| 块大小 | 256（必须 256 的倍数） | 与 SnapKV 默认 `R=257` 对齐；过小会增加 block_table 长度，过大会增加内部碎片 |
| 哈希算法 | xxhash64 + 三重校验 | 速度 ~10GB/s，加内容比对消除冲突误命中 |
| 释放策略 | 软回收 + 重置时清空 | 最大化前缀缓存命中率 |
| 数据结构 | `deque` (free) + `set` (used) + `dict` (hash) | 全部 O(1) 操作，规模到万级块也能稳定 |

---

## 🧾 1.5.10 一句话总结

> KvChat 的动态缓存块管理把一池物理块抽象为 **"分配 / 追加 / 截断 / 回收 / 共享"** 五种状态机操作，让 KV 压缩、抢占恢复和前缀缓存能在同一个 BlockManager 上无缝叠加。⚙️
