# 1.3 Flash-Attention ⚡

> **目标**：使用 [`flash-attn`](https://github.com/Dao-AILab/flash-attention) 提供的 IO-aware 融合算子，在 **Prefill / Decode** 两个阶段为 KvChat 提供高吞吐、低显存的注意力计算。

---

## 🧩 1.3.1 在项目中的位置

Flash-Attention 集中封装在：

```
KvChat/layers/attention.py  →  class Attention(nn.Module)
```

被 `KvChat/models/qwen3.py` 中的 `Qwen3Attention` 调用：

```python
o = self.attn(q, k, v, Layer)        # Layer 即层 id
```

`Attention` 内部统一处理三件事：

1. 🗄️ **写入 paged KV cache**（`store_kvcache` Triton kernel）
2. 🗜️ **可选 KV 压缩**（详见 `1.2 KV缓存压缩`）
3. ⚡ **调用 flash-attn 进行注意力计算**

---

## 🛣️ 1.3.2 双路径设计：Prefill vs Decode

```python
# KvChat/layers/attention.py
if context.is_prefill:
    o = flash_attn_varlen_func(...)        # 变长批 Prefill
else:
    o = flash_attn_with_kvcache(...)       # 单 token Decode + 分页 cache
```

### 🅿️ Prefill：`flash_attn_varlen_func`

适用场景：用户刚提交 prompt，需要为整段长度不一的序列一次性计算 attention。

```python
o = flash_attn_varlen_func(
    q, k, v,
    max_seqlen_q=context.max_seqlen_q,
    cu_seqlens_q=context.cu_seqlens_q,     # 累积长度索引
    max_seqlen_k=context.max_seqlen_k,
    cu_seqlens_k=context.cu_seqlens_k,
    softmax_scale=self.scale,
    causal=True,                           # 🔺 因果掩码
    block_table=context.block_tables       # 仅在前缀缓存命中时启用
)
```

数据准备过程见 `ModelRunner.prepare_prefill`：

```python
input_ids.extend(seq[seq.num_cached_tokens:])
positions.extend(range(seq.num_cached_tokens, seqlen))
cu_seqlens_q.append(cu_seqlens_q[-1] + seqlen_q)
cu_seqlens_k.append(cu_seqlens_k[-1] + seqlen_k)
```

特点 ✨：

| 维度 | 描述 |
| --- | --- |
| 📦 批结构 | **拼接式 Variable-Length**，所有序列 q/k/v 沿 token 维 concat |
| 🧮 索引 | 通过前缀和 `cu_seqlens_*` 区分批中各序列起止 |
| 🪄 前缀缓存 | 当 `cu_seqlens_k[-1] > cu_seqlens_q[-1]` 时（说明部分 KV 来自历史 cache），切到分页路径，用 `block_tables` 让 flash-attn 直接读取分页 cache |

### 🆑 Decode：`flash_attn_with_kvcache`

适用场景：每步只解码 1 个新 token，q 长度恒为 1，但需要从分页 KV cache 中读取整段历史。

```python
o = flash_attn_with_kvcache(
    q.unsqueeze(1),                      # [bs, 1, H, D]
    k_cache, v_cache,                    # 分页缓存张量
    cache_seqlens=context.context_lens,  # 每序列已 cache 的真实长度
    block_table=context.block_tables,    # 物理块映射表
    softmax_scale=self.scale,
    causal=True
)
```

数据准备过程见 `ModelRunner.prepare_decode`：

```python
input_ids.append(seq.last_token)
positions.append(seq.rope_pos)               # 真实时间线（不受 KV 压缩影响）
context_lens.append(len(seq))                # 当前可见 KV 长度
slot_mapping.append(block_table[-1] * block_size + last_block_num_tokens - 1)
```

特点 ✨：

| 维度 | 描述 |
| --- | --- |
| 🐎 单 token | q 形状 `[batch, 1, H, D]`，最大化单步延迟优势 |
| 🧱 分页读取 | 通过 `block_table` 在分散物理块之间跳转读取，无需整段连续显存 |
| 🗜️ 压缩协作 | 一旦 KV 被压缩，`context_lens` 立即更新为 `R`，flash-attn 只读这部分 |

## 🧪 1.3.3 数值类型策略

`ModelRunner.__init__` 中的核心选择：

```python
# KvChat/engine/model_runner.py
self.compute_dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
torch.set_default_dtype(self.compute_dtype)
```

| 选项 | 收益 |
| --- | --- |
| 🥇 **BF16**（A100/H100 优先） | 指数位与 FP32 等长，softmax 数值稳定，长序列优势明显 |
| 🥈 **FP16**（兜底） | 在不支持 BF16 的设备上保持兼容性 |

> Query Window 缓冲区也强制使用 `compute_dtype`，确保和 SnapKV 评分时的矩阵乘 dtype 一致，避免隐式转换。

## 🚀 1.3.4 启动期 Triton 预热

`warmup_triton_cache`（`model_runner.py`）在引擎启动时主动触发 `store_kvcache` 等 Triton kernel 的 JIT 编译：

```python
warmup_key   = torch.randn(4, num_kv_heads, head_dim, ...)
warmup_value = torch.randn(4, num_kv_heads, head_dim, ...)
store_kvcache(warmup_key, warmup_value, warmup_k_cache, warmup_v_cache,
              warmup_slot_mapping, block_size)
```

紧接着 `warmup_model()` 跑一次 `max_model_len` 长度的 prefill，把 `flash_attn_varlen_func` 也提前编译好。

⏱️ 估计收益：50–200ms 启动延迟下降。失败时只 warning，不影响主流程（"Graceful Fallback"）。

## 🧰 1.3.5 与 RoPE / GQA 的衔接

```python
# KvChat/models/qwen3.py · Qwen3Attention.forward
q, k = self.rotary_emb(positions, q, k)        # ① RoPE
o    = self.attn(q, k, v, Layer)               # ② Flash-Attn
output = self.o_proj(o.flatten(1, -1))
```

- ✅ **RoPE 在 attention 之前完成**：保证 flash-attn 拿到的是 rotary-applied 的 q/k。
- ✅ **GQA 支持**：`num_kv_heads < num_heads`，flash-attn 自动按组复制 K/V，免去手工展开；Tensor 并行下 `num_heads/world_size` 与 `num_kv_heads/world_size` 同时被切分（见 `QKVParallelLinear`）。

## 🧠 1.3.6 与 CUDA Graph / 压缩的协调

`run_model` 决定走 eager 还是 graph：

```python
need_eager_decode = (not is_prefill) and getattr(context, "compress_any", False)
if is_prefill or self.enforce_eager or not self.use_cuda_graph \
   or input_ids.size(0) > 512 or need_eager_decode:
    return self.model.compute_logits(self.model(input_ids, positions))   # eager
else:
    graph.replay()                                                       # CUDA Graph
```

⚠️ 一旦本步存在压缩动作（`compress_any=True`），KV cache 内容会被搬运、`context_lens` 会改变，**强制 eager**，避免 CUDA Graph 捕获到失效的张量地址。

---

## 🧾 1.3.7 一句话总结

> KvChat 用 **`flash_attn_varlen_func` 处理 Prefill 的拼接长批，用 `flash_attn_with_kvcache` 处理 Decode 的分页单步**，配合 BF16、Triton 预热与 CUDA Graph 选择性回退，构成了一套高吞吐、低显存且对长上下文友好的注意力子系统。🧨
