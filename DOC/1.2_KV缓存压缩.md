# 1.2 KV 缓存压缩 🗜️

> **目标**：在长上下文 Decode 阶段，通过 SnapKV 算法对 KV-Cache 进行**注意力打分 + Top-K 选择**式压缩，将 `S` 个历史 token 的 KV 缓存压缩为 `R` 个保留 token，以**显著降低显存占用**与**提升 Decode 吞吐**。

---

## 📐 1.2.1 总体设计

KvChat 的 KV 压缩特性由 **三个协同模块** 完成：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 🎯 触发与上下文 | `KvChat/engine/model_runner.py` (`prepare_compression_context`) | 决定哪些序列在本步需要压缩 / 维护 Query Window |
| 📊 重要性评估 | `KvChat/layers/CompressMethod.py` (`SnapKV`) | 基于注意力得分给出保留 token 的相对索引 |
| 🚚 物理搬运 | `KvChat/layers/compress_utils.py` (`MyCompressCompact` + Triton kernel) | 将选中的 KV 行就地紧凑到块前部，并发出 `compression_events` |

调度器在 step 后通过 `compression_events` 释放尾部 block（见 `Scheduler.postprocess`、`BlockManager.truncate_blocks`）。

---

## ⚙️ 1.2.2 关键参数

定义于 `KvChat/config.py` 的 `Config.__post_init__`：

```python
# 12. Auto-compute compression thresholds
self.kv_compress_S = self.kvcache_block_size * (self.kv_compress_N + 1) - 1
self.kv_compress_R = self.kvcache_block_size * self.kv_compress_N + 1
```

| 参数 | 含义 | 计算公式 |
| --- | --- | --- |
| `kvcache_block_size` | 单个 KV-Cache 物理块的 token 数（必须是 256 倍数） | 默认 `256` |
| `kv_compress_N` | 压缩后保留的"完整块数" | 默认 `1` |
| `kv_compress_S` | **触发阈值**：当某序列长度 `L == 用户prompt长度 + S` 时触发本轮压缩 | `block_size * (N+1) - 1` |
| `kv_compress_R` | **保留长度**：压缩后 KV 上下文长度（含 BOS、保留中间 token、Window） | `block_size * N + 1` |
| `query_window_size` | SnapKV 评分所用的"近窗口 query 数" | 默认 `50` |

> 默认 `block_size=256, N=1` ⇒ `S=511, R=257`，即每当 KV 上下文增长到 `prompt_len + 511` 时触发一次压缩，将其压缩到 `prompt_len + 257`。📉

参数也可通过 `SamplingParams` 中的 `compress_S` / `compress_R` 在请求级别覆盖（见 `KvChat/sampling_params.py`）。

## 🚦 1.2.3 触发逻辑：何时压缩？

`ModelRunner.prepare_compression_context` 在每个 **decode step** 的预处理阶段被调用：

```python
# KvChat/engine/model_runner.py
for i, seq in enumerate(seqs):
    seq_ids.append(seq.seq_id)
    S_i = seq.num_prompt_tokens + self.config.kv_compress_S
    R_i = seq.num_prompt_tokens + self.config.kv_compress_R
    L = len(seq)
    need_compress = (L == S_i)                # 🎯 严格等于触发，避免重复压缩
    active = (L > S_i - W) and (L <= S_i)      # 📥 进入近窗口，开始记录 Query
```

- `need_compress`：标记本步此序列**需立即压缩**，写入 `ctx.compress_need_mask`。
- `active`：标记本步此序列处于 **Query Window 收集阶段**（最后 `W` 个 query）。
- 一旦某序列首次进入 active 区间，立即调用 `query_window_manager.activate(seq_id)` 在显存中开辟一段环形缓冲区。

整体时间线 ⏱️：

```
prompt 生成 ──┬── 普通 decode ───────┬─[active]─ 收集 W 个 query ─┐
              0..(S-W)                S-W            S            ▼
                                                     触发压缩 → 释放尾部 block
```

## 🪟 1.2.4 Query Window：SnapKV 的"打分材料"

实现位于 `KvChat/engine/query_window_manager.py`：

- **`QueryWindowBuffer`** 为每个序列分配 `[num_layers, W, num_heads, head_dim]` 的 GPU 张量，使用**环形写指针** `write_pos` 记录最近 `W` 个解码步骤的 query。
- **`append(seq_ids, layer_id, q)`** 在 `Attention.forward` 中被调用，仅对处于 active 状态的序列追加；只有当写到最后一层时 `write_pos` 才前进，保证 32 层对齐。
- **`gather(seq_ids, layer_id)`** 在压缩时取出 `[m, Hq, W, D]` 形状的近窗口 query，作为 SnapKV 输入。

> 📝 设计亮点：Query Window 让 SnapKV 不必使用"当前唯一的 query"做评分，而是用近窗口的 W 个 query **平均效应**评估每个历史 token 的重要性，鲁棒性更强。

## 🧠 1.2.5 SnapKV 算法核心

`KvChat/layers/CompressMethod.py`：

```python
def SnapKV(Q, K, V, num_keep=220, window=5):
    # Q: [B, Hq, W, D]   K/V: [B, Hk, L, D]
    if L - window <= 0 or L <= num_keep + window:
        return False                                  # ✋ 太短，跳过
    K_cut = K[:, :, :-window, :]                     # 排除最近 window
    attn_scores = Q @ K_cut^T * scale                # GQA 分组矩阵乘
    attn_scores[:, :, :, 0] = -inf                   # 🚫 抑制 attention sink
    attn_probs = softmax(attn_scores, dim=-1)
    key_importance = attn_probs.sum(dim=2)            # 沿 query 维聚合
    if Hq > Hk: key_importance.sum(dim=1, keepdim=True)
    idx_keep = topk(key_importance, k=num_keep).sorted()
    return [BOS] ⊕ idx_keep ⊕ [tail_window]
```

特性 ✨：

1. **GQA 友好**：当 `Hq != Hk` 时按 group 分块矩阵乘，避免 K 重复展开。
2. **Attention Sink 屏蔽**：将位置 0（BOS）的得分手动置 `-inf`，最后单独以 BOS 索引拼回，防止整张得分图被首 token 主导。
3. **结构化保留**：`final_idx = [BOS] + Top-K中间 + [最后 window 个]`，长度恰为 `1 + num_keep + window`。

实际调用：

```python
keep_idx = SnapKV(q_sub, k_sub, v_sub,
                  window = query_window_size,
                  num_keep = R - query_window_size - 1)
```

## 🚚 1.2.6 物理压缩：`MyCompressCompact`

完成 **"评分→选择→搬运→事件上报"** 流水线：

### Step 1 · 收集 K/V 来源

```python
seq_idxs = torch.nonzero(mask_tensor)[0]      # 本批中 need_compress 的下标
k_sub, v_sub = TritonGetKVForComp(...)        # 调用 chunked Triton kernel
```

`TritonGetKVForComp`（`compress_utils.py:_gather_kv_chunk_kernel`）按 `chunk_size=128` 分片地从 paged KV cache 抽取每序列最近 `S` 个 token，返回 `[m, Hk, S, D]`。

### Step 2 · 计算源/目标槽位

```python
slots_per_block = block_tables.unsqueeze(-1) * block_size + offsets   # 每槽绝对位置
src_slots = slots_flat.gather(1, start_idx + range(S))                # 源 S 槽
keep_blocks = ceil(R / block_size)
dest_blocks = block_tables[seq_idxs, :keep_blocks]                    # 目标块
```

> 💡 通过 `(seq_lens - S).clamp(min=0)` 实现"取最近 S 个 token"的左对齐，让批内序列长度差异可统一处理。

### Step 3 · 就地搬运 KV

```python
vals_k = k_flat.index_select(0, src_flat).clone()  # ⚠️ clone 防覆写
vals_v = v_flat.index_select(0, src_flat).clone()
k_flat.index_copy_(0, dst_flat, vals_k)            # 紧凑到前 R 个槽位
v_flat.index_copy_(0, dst_flat, vals_v)
context.context_lens[seq_idxs] = R                 # 🎯 更新本步可见 KV 长度
```

> ⚠️ 仅修改 `context.context_lens` 而不修改 `seq.rope_pos`：RoPE 必须始终使用真实的 token 时间线，不能因压缩而"回退"。这一点在 `prepare_decode` 中通过 `positions.append(seq.rope_pos)` 严格保证。

### Step 4 · 事件上报（最后一层时）

```python
if layer_id + 1 >= num_layers:
    freed_blocks = context.block_tables[seq_idxs, keep_blocks:]
    context.compression_events.append({
        "batch_index": ..., "R": R, "keep_blocks": keep_blocks,
        "freed_block_ids": [...]
    })
    for sid in compress_seq_ids: query_window_manager.free(sid)
```

只在最后一层发出事件，避免每层重复上报；同时主动释放 Query Window 缓冲区，节省显存 🧹。

## 🔁 1.2.7 与调度器的协作

`Scheduler.postprocess`（`KvChat/engine/scheduler.py`）消费事件：

```python
for ev in compression_events:
    seq = seqs[ev["batch_index"]]
    self.block_manager.truncate_blocks(seq, ev["keep_blocks"])  # 释放尾块
    seq.num_tokens = ev["R"]                                    # 逻辑长度同步
```

`BlockManager.truncate_blocks` 把 `block_table[keep_blocks:]` 的引用计数减 1，归零的物理块送回 `free_block_ids`，并把新尾块的 `hash` 置 `-1`（因为它内容已被改写，不再可作为前缀缓存匹配）。

## 📊 1.2.8 性能与精度收益

- 💾 **显存**：单序列 KV 上下文从 `S=511 → R=257`（默认 N=1），实际占用近乎对半减少；连续多轮压缩可让 32k 上下文常驻显存。
- ⚡ **吞吐**：Decode 阶段 attention 复杂度与 KV 长度近似线性，KV 越短单步越快。
- 🎯 **质量**：SnapKV 论文已证明 Top-K + Tail-Window + BOS 的策略能在长上下文上保持极小困惑度损失。
- 🛡️ **可控**：通过 `chat.py` 的 `/compress on|off` 命令可在任意时刻热切换；通过 `SamplingParams` 可按请求粒度覆盖 `S/R`。

---

## 🧷 1.2.9 一句话总结

> KvChat 的 KV 压缩是一条 **"近窗口 Query → SnapKV 评分 → Triton 紧凑搬运 → BlockManager 回收"** 的自动化流水线，把"长上下文显存爆炸"问题工程化地落地成一个**每 256 token 一次**的轻量例程。✨
