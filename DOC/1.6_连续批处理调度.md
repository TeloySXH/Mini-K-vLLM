# 1.6 连续批处理调度 🚦

> **目标**：参照 vLLM 的 Continuous Batching 思想，让 Prefill 与 Decode **共用一个调度器**，通过"两阶段优先级"在每一步选出可执行批次，最大化 GPU 利用率并保证延迟可控。

---

## 🧭 1.6.1 调度器在系统中的位置

```
chat.py / generate()
   │
   ▼
LLMEngine.step()                  ← KvChat/engine/llm_engine.py
   ├── scheduler.schedule()       ← 选批：返回 (seqs, is_prefill)
   ├── model_runner.call("run")   ← 跑批：返回 (token_ids, compression_events)
   └── scheduler.postprocess()    ← 收尾：写回 token、释放块、处理 EOS
```

调度器对外接口非常精简：

```python
# KvChat/engine/scheduler.py
class Scheduler:
    def add(seq)                        # 提交新请求
    def schedule() -> (seqs, is_prefill)# 选出本步批次
    def postprocess(seqs, token_ids, compression_events)
    def preempt(seq)                    # 显存不足时降级
    def is_finished()                   # 全局退出条件
```

---

## 🧩 1.6.2 数据结构：从 deque 到 heap

```python
self.waiting_heap: list[tuple]       # min-heap by len(seq)
self.waiting_dict: dict[int, Sequence]
self.running:      deque[Sequence]   # 双端队列，便于头尾操作
```

| 队列 | 数据结构 | 选用理由 |
| --- | --- | --- |
| `waiting_heap` | 最小堆 (`heapq`) | **优先调度短序列**，prefill 延迟更低；插入/弹出 O(log n) |
| `waiting_dict` | 哈希表 | 与 heap 配合做 O(1) 反查、抢占重入 |
| `running` | `deque` | 头部 popleft 公平轮转、尾部 pop 抢占最新进入者 |

> 🎯 设计动机：在传统 deque-only 实现中，挑短序列要 O(n)；引入 heap 后即使"等待队列上千"也能稳定 O(log n)。

---

## 🧠 1.6.3 两阶段调度算法

`Scheduler.schedule()` 分为 **Prefill 优先** + **Decode 兜底** 两阶段：

### Phase 1 · Prefill 选批

```python
while waiting_heap and num_seqs < max_num_seqs:
    length, seq_id, seq = heapq.heappop(waiting_heap)
    del waiting_dict[seq_id]

    if num_batched_tokens + length > max_num_batched_tokens:
        heapq.heappush(waiting_heap, (length, seq_id, seq))   # ❎ 超 batch token 上限，回插
        break
    if not block_manager.can_allocate(seq):
        heapq.heappush(waiting_heap, ...)                     # ❎ 块不够，下一轮再说
        continue

    block_manager.allocate(seq)                               # ✅ 分配 KV blocks
    num_seqs += 1
    num_batched_tokens += length - seq.num_cached_tokens      # 仅未缓存部分计数（前缀缓存收益）
    seq.status = RUNNING
    self.running.append(seq)
    scheduled_seqs.append(seq)

if scheduled_seqs:
    return scheduled_seqs, True                               # 🅿️ Prefill 模式
```

约束 ⛔：

| 限制 | 配置项 |
| --- | --- |
| 最大并发序列数 | `Config.max_num_seqs` |
| 单步累计 token 上限 | `Config.max_num_batched_tokens` |
| 块预算 | `BlockManager.free_block_ids` |

🧠 关键：`num_batched_tokens += length - num_cached_tokens` —— 命中前缀缓存的部分**不计入预算**，让"重复 system prompt"几乎零成本进入批次。

### Phase 2 · Decode 选批 + 抢占

```python
while running and num_seqs < max_num_seqs:
    seq = running.popleft()

    while not block_manager.can_append(seq):     # 显存不足以追加新块
        if running:
            preempt_seq = running.pop()          # 抢占"最新加入"
            self.preempt(preempt_seq)
        else:
            self.preempt(seq); break             # 无人可抢，自己降级

    if can_allocate or block_manager.can_append(seq):
        block_manager.may_append(seq)
        scheduled_seqs.append(seq); num_seqs += 1
    else:
        running.appendleft(seq); break

# 收尾：把已选序列重新放回 running（保持原顺序）
self.running.extendleft(reversed(scheduled_seqs))
return scheduled_seqs, False                     # 🆑 Decode 模式
```

🛡️ 抢占哲学："**LIFO 抢占**"——优先牺牲最近进入 running 的序列，保留更早进入者，避免老请求长时间饥饿。

## 🧪 1.6.4 Prefill 与 Decode 的"互斥每步"

```python
if scheduled_seqs:
    return scheduled_seqs, True   # 本步只跑 Prefill
...
return scheduled_seqs, False      # 否则只跑 Decode
```

KvChat **不在同一步混合 Prefill 与 Decode**，原因：

- Prefill 走 `flash_attn_varlen_func`、Decode 走 `flash_attn_with_kvcache`，kernel 不同。
- Prefill 输入是变长拼接，Decode 是 `[bs, 1]`；混合会大幅增加 kernel 调度复杂度。
- 通过"每步只挑一种"，保持 CUDA Graph 仅捕获 Decode 形状，提高复用率。

> ⚖️ 这是延迟与吞吐的折中：偶尔的 prefill 会暂停 decode 一步，但换来了 graph 命中率与代码简洁度。

## 🔁 1.6.5 后处理：`postprocess()`

```python
# 1. 处理 KV 压缩事件
if compression_events:
    for ev in compression_events:
        seq = seqs[ev["batch_index"]]
        block_manager.truncate_blocks(seq, ev["keep_blocks"])
        seq.num_tokens = ev["R"]

# 2. 写回新生成 token
for seq, token_id in zip(seqs, token_ids):
    seq.append_token(token_id)
    if (token_id == eos and not seq.ignore_eos) \
       or seq.generated_completion_tokens == seq.max_tokens:
        seq.status = FINISHED
        block_manager.deallocate(seq)
        running.remove(seq)
```

要点 ✨：

- 🗜️ **压缩事件先于 token 写回**：保证 `seq.num_tokens` 与 paged cache 中的真实长度同步。
- ✅ **EOS / max_tokens 终止**：触发条件由 `Sequence.generated_completion_tokens` 累加器精准控制（不是 `len(seq)`，因压缩可能改变 `num_tokens`）。
- 🧹 终止序列立即归还块，让显存尽快释放给等待队列。

## ⚡ 1.6.7 step() 的完整数据流

```python
# KvChat/engine/llm_engine.py
def step(self):
    seqs, is_prefill = self.scheduler.schedule()

    perf_monitor.start_timer(f"{'prefill' if is_prefill else 'decode'}_kernel")
    self.model_runner.call("set_compress_enabled", config.kv_compress_enabled)
    token_ids, compression_events = self.model_runner.call("run", seqs, is_prefill)
    elapsed_ms = perf_monitor.end_timer(...)

    self.scheduler.postprocess(seqs, token_ids, compression_events)
    # 累加 prefill_tokens / decode_tokens / 时间 / 最大 batch 等
    return outputs, num_tokens, step_token_ids, None, None
```

🌀 **持续循环**：`chat.py` 中 `while not llm.is_finished(): llm.step()`，让本批一边 decode、一边接收新请求（在多请求模式下 `add_request` 会立即进入 `waiting_heap` 参与下一次 `schedule`）。

## 🧾 1.6.8 一句话总结

> KvChat 的连续批处理调度器以 **"短序列优先 prefill + LIFO 抢占式 decode + 两阶段互斥每步"** 为核心策略，配合 heap/deque 双队列与精确的 token 预算，把 GPU 时刻喂满，又把单请求的尾部延迟控制在可接受的范围。🚀
