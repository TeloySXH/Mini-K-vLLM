# 1.4 Paged Attention 📑

> **目标**：参照 vLLM 的 Paged KV-Cache 思想，将 KV 缓存切分为定长**物理块（Block）**，通过 `block_table` 把"逻辑序列"映射到"分散物理块"，从而消除显存碎片并支持任意长度的 KV 共享与压缩。

---

## 🏗️ 1.4.1 物理布局

`ModelRunner.allocate_kv_cache`（`KvChat/engine/model_runner.py`）一次性分配整段 KV 缓存：

```python
self.kv_cache = torch.empty(
    2,                          # 0=K, 1=V
    hf_config.num_hidden_layers,
    config.num_kvcache_blocks,  # 总块数（自适应显存）
    self.block_size,            # 每块 token 数 (默认 256)
    num_kv_heads,
    head_dim
)

for module in self.model.modules():
    if hasattr(module, "k_cache"):
        module.k_cache = self.kv_cache[0, layer_id]
        module.v_cache = self.kv_cache[1, layer_id]
        layer_id += 1
```

📐 形状语义：

```
 ┌─────── 2 ───────┐
 │ K cache | V cache│        ← 第 0 维：键/值
 │  L 层   |  L 层  │        ← 第 1 维：层
 │  N 块   |  N 块  │        ← 第 2 维：物理块
 │  256 t  |  256 t │        ← 第 3 维：块内 token 槽
 │  Hk     |  Hk    │        ← 第 4 维：KV 头
 │  D      |  D     │        ← 第 5 维：head_dim
 └─────────────────┘
```

每层的 `k_cache` 是一个张量切片（无拷贝），后续所有读写都通过 `slot = block_id * block_size + offset` 寻址。

## 🧮 1.4.2 块数量自动估算

```python
# KvChat/engine/model_runner.py
free, total = torch.cuda.mem_get_info()
current     = torch.cuda.memory_stats()["allocated_bytes.all.current"]
block_bytes = 2 * num_layers * block_size * num_kv_heads * head_dim * 4   # FP32 估算
available   = int(total * config.gpu_memory_utilization) - current
config.num_kvcache_blocks = max(1, available // block_bytes)
```

策略 🔍：

- 以 `gpu_memory_utilization`（默认 0.8）为预算上限。
- 用 **FP32 字节数**保守估算单块大小，留出实际激活、临时缓冲与 CUDA Graph 池所需的余量。
- 显存极度不足时**降级到 1 块**并打印 warning，保证 chat.py 不直接崩溃。

## 🔢 1.4.3 序列侧的视图：`block_table`

`Sequence`（`KvChat/engine/sequence.py`）维护两个关键属性：

| 属性 | 含义 |
| --- | --- |
| `block_table: list[int]` | 该序列依次占用的物理块 id |
| `num_cached_tokens` | 已经写入分页 cache 的 token 数（通常按整块对齐） |

辅助 property：

```python
num_blocks          = ceil(num_tokens / block_size)
num_cached_blocks   = num_cached_tokens // block_size
last_block_num_tokens = num_tokens - (num_blocks - 1) * block_size
def block(i): return token_ids[i*block_size : (i+1)*block_size]
```

**逻辑→物理映射**：第 `i` 个逻辑块的物理位置即 `block_table[i]`，分页 cache 中起始 slot = `block_table[i] * block_size`。

## 🪪 1.4.4 Slot 寻址 & `slot_mapping`

每次模型 forward 都需要告诉 Triton kernel：**当前要写的每个 token 应落到 cache 的哪个绝对槽位**。

### Prefill 段

```python
# ModelRunner.prepare_prefill
for i in range(seq.num_cached_blocks, seq.num_blocks):
    start = seq.block_table[i] * self.block_size
    end   = start + (block_size if i != last else last_block_num_tokens)
    slot_mapping.extend(range(start, end))
```

### Decode 段

```python
# ModelRunner.prepare_decode
slot_mapping.append(
    seq.block_table[-1] * self.block_size + seq.last_block_num_tokens - 1
)
```

随后 `store_kvcache_kernel`（`KvChat/layers/attention.py`）对 `slot_mapping == -1` 的位置静默跳过，对其余按公式：

```
block_idx     = slot // block_size
block_offset  = slot %  block_size
addr = block_idx * (block_size * Hk * D) + block_offset * (Hk * D) + head_idx * D
```

把 `(num_tokens, Hk, D)` 形状的新 K/V 写入 paged cache。

## 🚪 1.4.5 块分配器 `BlockManager`

实现于 `KvChat/engine/block_manager.py`，是 paged attention 的"内存管理器"。

### 数据结构

```python
self.blocks: list[Block]                       # 全部物理块
self.free_block_ids: deque[int]                # 空闲块队列
self.used_block_ids: set[int]                  # 已占用块
self.hash_to_block_id: dict[int, int]          # 内容寻址：哈希→块 id（前缀缓存）
```

每个 `Block` 保存 `ref_count, hash, token_ids`，支持引用计数式的共享。

### 关键 API

| API | 触发时机 | 作用 |
| --- | --- | --- |
| `can_allocate(seq)` | Scheduler 准入新序列 | 校验 `free_block_ids ≥ seq.num_blocks` |
| `allocate(seq)` | Scheduler 进入 Prefill | 哈希命中→共享，未命中→分配新块；写入 `seq.block_table` |
| `can_append(seq)` | Decode 步预检 | 当 `len(seq) % block_size == 1` 时需追加新块 |
| `may_append(seq)` | Decode 步实际执行 | 满块时刷新 hash 写入 dict；新建块时从 `free_block_ids` 弹出 |
| `deallocate(seq)` | 序列结束 / 抢占 | 引用计数减 1，归零的块回收 |
| `truncate_blocks(seq, k)` | KV 压缩事件 | 释放 `block_table[k:]`、把新尾块 hash 置 -1 |

### 前缀缓存（Prefix Cache）🔁

```python
# allocate(seq)
h = compute_hash(token_ids, prefix_h)
block_id = hash_to_block_id.get(h, -1)

# Triple verification
if block_id != -1 and block.hash == h and block.token_ids == token_ids:
    seq.num_cached_tokens += block_size
    block.ref_count += 1                # ✅ 命中：直接共享
else:
    # 未命中或冲突：分配新块
    block_id = self.free_block_ids[0]
    block = self._allocate_block(block_id)
```

亮点 ✨：

- 🔐 **三重校验**：哈希值 + 内容 token_ids + 引用计数，防止 `xxhash` 冲突误命中。
- 📊 **冲突统计**：`collision_stats` 记录碰撞数，便于诊断长时间运行下的哈希分布。
- 🪶 **零拷贝复用**：相同前缀的多请求共享物理块（多轮对话首条 system prompt 即受益）。

## 🧊 1.4.6 块表传给 Kernel：`prepare_block_tables`

```python
def prepare_block_tables(self, seqs):
    max_len = max(len(seq.block_table) for seq in seqs)
    block_tables = [
        seq.block_table + [-1] * (max_len - len(seq.block_table))
        for seq in seqs
    ]
    return torch.tensor(block_tables, dtype=torch.int32, pin_memory=True).cuda(non_blocking=True)
```

📌 设计要点：

- 用 `-1` 右填充把不规则 `block_table` 统一成矩形 `[bs, max_blocks]`，方便 flash-attn / Triton kernel 索引。
- `pin_memory + non_blocking` 实现 **CPU→GPU 异步拷贝**，与 `slot_mapping`、`positions` 等张量并行传输，节省一次 H2D 同步开销。

flash-attn 通过该 `block_table` 自动跳跃读取分散物理块；KV 压缩 kernel 通过它定位源/目标 slot。

## 🧯 1.4.7 抢占（Preemption）流程

当 Decode 时显存不够追加新块（`can_append == False`）：

```python
# Scheduler.schedule
preempt_seq = self.running.pop()
self.preempt(preempt_seq)         # → block_manager.deallocate + heappush(waiting)
```

`preempt` 把序列状态恢复成 `WAITING`、释放它的 `block_table`、并放回 `waiting_heap`，等待后续重新排队。这避免了"卡死"，保证最坏情况下系统仍能前进。

## 🛡️ 1.4.8 与 CUDA Graph 的兼容

`capture_cudagraph` 时使用 `max_num_seqs × max_num_blocks` 的"满尺寸"块表占位张量：

```python
block_tables = torch.zeros(max_bs, max_num_blocks, dtype=torch.int32)
```

每次 replay 之前通过 `graph_vars["block_tables"][:bs, :context.block_tables.size(1)] = ...` 填入当前批的真实块表，让相同 graph 适配不同序列长度，**变形而不重新捕获**。

## 🧾 1.4.9 一句话总结

> Paged Attention 通过 **"定长物理块 + 序列级 block_table + 哈希前缀缓存 + slot_mapping 写入"** 四件套，把传统 KV-Cache 的"连续大张量"重构为"碎片化但可寻址"的池化资源，是 KvChat 支撑长上下文、KV 压缩与高并发的根基。🧱
